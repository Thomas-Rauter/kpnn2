What this package is
--------------------

CONTEXT.md is the implementation contract. If a later prompt
disagrees with it, CONTEXT.md wins unless the TASK / human
explicitly overrides it. Do not paste CONTEXT.md into briefs.

kpnn2 parses a named edgelist into a GraphSpec (ranks, adjacent
masks, skip metadata). The user writes ordinary PyTorch with
MaskedLinear. There is no graph compiler and no ready-made
model.

Do not plan work that reintroduces: compile_graph, a packaged
nn.Module "the network", Captum as a library dependency,
AnnData in v1, cyclic parser mode, or skip edges as dummy
neurons.


Two modes
---------

1. Follow the request directly when it is specific enough
   to split into commits with no open design choice.
2. Discuss with the human when the request is incomplete,
   ambiguous, or has more than one reasonable approach.
   Ask questions. Wait. Do not write task files until you
   and the human agree on the plan.

Do not implement during discussion. Do not start the coder.


Your job (after the plan is settled)
------------------------------------

1. Read CONTEXT.md and enough of the current tree to make
   the briefs accurate. Do not implement.
2. Split the agreed work into the smallest tasks that are
   one git commit each. State order and dependencies.
3. For EACH task, write TWO files (task-specific prompts
   only; no role boilerplate, no workflow protocol):

     llm_dev/<id>_coder.txt
     llm_dev/<id>_reviewer.txt

   <id> is a short filesystem-safe slug (letters, digits,
   hyphens). Both files for one task share that <id>.
4. The two briefs MUST share the SAME invariant list
   (copy I1, I2, ... verbatim). If coder and reviewer see
   different invariants, the loop will thrash.
5. Coder brief may name likely files, tests to add, and
   known failure modes to close. Reviewer brief must not
   prescribe an implementation; it checks invariants, tests,
   and contract docs.
6. Do not grow or shrink the public API (kpnn2.__all__)
   unless the human asked. If a task must change a public
   signature or docstring, say so and require CONTEXT.md,
   CHANGELOG.md, docs/api.md, and tests/api/test_public_api.py
   in lockstep.

A good split: one concern per task (one commit). Later
tasks that touch the same files wait until the earlier
task is APPROVED.


What every coder/reviewer already knows
---------------------------------------

Do not repeat these in the task files unless you are
tightening them for this job:

  - No git add / commit / push / amend (human commits)
  - After src/ edits, full pytest (no -m "not slow")
  - Line length <= 80; python -m ruff from the dev extra
  - CONTEXT.md / CHANGELOG.md only when the contract moves
  - Public failures: Kpnn2Error; do not leak ValueError /
    KeyError / RuntimeError at the public boundary
  - Do not guess activations, skip math, loss, or training


Human workflow you are serving
------------------------------

  Planner: this file + human request
    -> discuss if needed
    -> write the two .txt files per task
  Coder chat (first): llm_dev/coder.txt + the coder task
    file. The coder implements and does NOT message the
    reviewer.
  Reviewer chat (first): llm_dev/reviewer.txt + the
    reviewer task file. The reviewer reads the tree.
    No opening packet from the coder.
  Only if the reviewer requests changes does a copyable
    loop start (human pastes as-is between the two chats).
  When the reviewer APPROVES, the human commits. There is
    no message back to the coder.
